# 00. 개요

**Situation**

이전에 개별 시뮬레이션 5개와 대시보드 2개를 따로 만든 적이 있다. 각각은 나름의 결과를 냈지만,
막상 "그래서 이 라인의 OEE가 몇 %인가"라는 질문을 받으면 하나의 숫자로 답할 수 없었다.
시뮬레이션마다 출력 형식이 다르고, 어떤 결과는 실측값이고 어떤 결과는 가정치인지 구분이
안 되어 있었기 때문이다. 현장에서 설비종합효율(OEE)은 가동률·성능·품질을 곱한 단일 지표로
관리되는데, 내가 만든 결과물들은 이 세 축으로 정리조차 되어 있지 않았다.

**Task**

이번 프로젝트의 목표는 두 가지였다.
1. 여러 분석 결과를 표준 KPI 계약(스키마)으로 통합해서, "OEE = 가동률(A) × 성능(P) × 품질(Q)"
   하나의 구조로 언제든 답할 수 있게 만든다.
2. 실측 정비이력(MTBF/MTTR)을 가상라인 시뮬레이션에 주입해서, "버퍼를 늘리면?", "PM 주기를
   바꾸면?" 같은 질문에 추측이 아니라 실행 가능한 시뮬레이션으로 답한다.

**Action / Result**

STEP 0~13을 거치며 데이터 소싱 → KPI 표준화 → SimPy 디지털트윈 → Streamlit 대시보드 → 배포까지
전 과정을 실제로 실행하고 검증했다. 아래 01~07에 각 단계와 실제 수치, 그 과정에서 만난
버그·발견을 정리했다.

> 원래 계획은 기존에 만들어둔 시뮬레이션 자산(sim1~sim5)을 재활용하는 것이었지만, 실제
> 작업 환경에 그 자산이 없다는 걸 초반에 확인했다. 그래서 SimPy 가상라인과 스케줄링 로직을
> 처음부터 새로 설계했다 — 이 판단과 그 근거는 01에서 이어서 설명한다.

# 02. KPI 표준화 — OEE = A × P × Q 분해와 데이터 계약 설계

## 왜 필요했나

여러 시뮬레이션·모델이 각자 다른 형식으로 결과를 내면, 나중에 "지금 이 라인 상태가 좋은지
나쁜지"를 판단할 때마다 매번 새로 해석해야 한다. 그래서 모든 결과를 하나의 스키마로 강제했다.

## KPI 데이터 계약 (`src/kpi/schema.py`)

```
scenario_id, source, process, kpi_name, kpi_value, unit, ci_low, ci_high, run_id, timestamp
```

- `kpi_name`은 19개로 화이트리스트 관리(`ALLOWED_KPIS`) — 아무 문자열이나 못 들어가게 막음
- 비율형 KPI(`RATIO_KPIS`)는 0~1 범위를 벗어나면 검증 실패
- `validate_kpi()`가 5가지(컬럼 누락, dtype, 미등록 kpi_name, 비율 범위, CI 역전)를 자동 점검
- `append_kpi()`는 `drop_duplicates(subset=[scenario_id, source, process, kpi_name], keep="last")`로
  같은 조합을 재실행해도 중복 없이 최신값으로 덮어씀 (이 로직이 왜 필요했는지는 06번 STAR 참고)

## OEE 계산식 (`src/kpi/calc.py`)

```
가동률(A) = 가동시간 / 계획시간
성능(P)   = (이론 사이클타임 × 생산량) / 가동시간
품질(Q)   = 양품수 / 총생산수
OEE = A × P × Q
```

이 세 축으로 분해해두면, 예를 들어 OEE가 낮게 나왔을 때 "가동률 문제인지 성능 문제인지
품질 문제인지"를 바로 구분해서 원인을 좁힐 수 있다 — 이후 03·04에서 이 구조를 그대로
활용한다.

# 03. 디지털트윈 시뮬레이션 — 실측 MTBF/MTTR을 SimPy 가상라인에 주입

## 실측 MTBF/MTTR (STEP 3)

Azure PdM의 failures·maint 실측 이력에서 부품별(comp1~4) MTBF/MTTR을 직접 계산했다.

| 부품 | MTBF (시간) | MTTR (시간) | 고장 건수 |
|---|---:|---:|---:|
| comp1 | 3,045.16 | 36.02 | 192 |
| comp2 | 2,561.57 | 23.20 | 259 |
| comp3 | 2,176.39 | 24.44 | 131 |
| comp4 | 2,328.66 | 12.65 | 179 |
| (설비 전체 평균) | 1,410.72 | 19.98 | — |

전체 설비(100대) 평균 Availability는 **98.21%**다.

## 5공정 가상라인 설계 (`src/simulation/line_sim.py`)

공정 5개(가공1·가공2·열처리·조립·검사)로 구성된 가상라인을 SimPy로 만들고, 위 부품별
MTBF/MTTR을 공정에 매핑해 고장·PM(예방보전)·유한버퍼·불량을 시뮬레이션했다. 사이클타임
(45/50/60/55/40초)은 실측이 아니라 설계 가정치라는 걸 명확히 문서화해뒀다(열처리 60초가
병목).

기준 시나리오(8시간 교대, 버퍼 5, PM 없음) 몬테카를로 30회 결과:

| KPI | 값 |
|---|---:|
| OEE | 99.17% |
| 가동률(A) | 100.00% |
| 성능(P) | 99.17% |
| 품질(Q) | 100.00% |
| UPH | 59.5 |
| 병목공정 | 열처리 (사이클타임 60초) |

## 시나리오 그리드 (STEP 7) — 버퍼×PM 30개 조합

`build_scenarios.py`로 버퍼 용량(0/2/5/10/15/20) × PM 주기(0/200/400/800/1600분) 30개
조합을 각 30회 몬테카를로로 돌렸다(총 소요 20.3초). 결과가 처음엔 "버그처럼" 보였는데,
실제로는 진짜 발견이었다:

- **버퍼 0~20 전 구간에서 OEE가 0.991667로 완전히 동일**했다. 8시간(480분) 시프트 안에서는
  실측 MTBF(수천 시간대)가 너무 커서 고장이 거의 발생하지 않고, 고장이 없으면 버퍼가
  흡수할 변동 자체가 없다. 버퍼는 "변동을 흡수"하는 역할이라, 변동이 없는 조건에서는
  크기를 늘려도 효과가 안 보이는 게 정상이다.
- **PM 주기 800·1600분에서 Availability가 갑자기 100%로 튀었다.** PM 주기가 관측 기간
  (480분)보다 길면 그 창 안에서 PM이 한 번도 발생하지 않으니 당연한 결과다(PM 200분:
  87.5%, PM 400분: 93.1%로 정상적인 경계 효과).

## 생산계획 — FCFS vs SPT (`src/simulation/scheduling.py`)

6개 잡을 5공정 플로우샵에서 FCFS(선입선출)와 SPT(최단처리시간 우선) 규칙으로 각각
스케줄링했다. "SPT가 항상 더 낫다"는 통념과 반대로:

| 규칙 | 메이크스팬 |
|---|---:|
| FCFS | 575.9초 |
| SPT | 1038.6초 (+80.3%) |

원인은 SPT를 공정마다 독립적으로 적용하면 특정 잡(여러 공정에서 처리시간이 긴 잡)이 매
공정마다 계속 뒤로 밀려 대기시간이 누적되기 때문이다(현장의 "장기물 방치" 문제와 같은
메커니즘). SPT는 단일공정 평균흐름시간 최적화엔 유리하지만 다단계 플로우샵의 메이크스팬은
보장하지 못한다.

## 비용민감 예지보전 모델 (STEP 8, APS Scania)

과검(FP)=10, 미검(FN)=500으로 비대칭 비용을 설정하고 임계값을 스위핑했다.

| 모델 | 임계값 | Recall | Precision | 총비용 |
|---|---:|---:|---:|---:|
| 더미(전부 정상) | — | 0.0% | — | 187,500 |
| 기본 RF | 0.50 | 74.4% | 83.0% | 48,570 |
| **비용최적 RF** | **0.05** | **99.2%** | 34.2% | **8,670** |

더미 대비 **178,830(95.4%) 절감**. 다만 Precision 34.2%가 뜻하는 건 "과검이 여전히 많다"는
것 — 클래스 불균형(pos 1.67~2.34%)을 완전히 없앤 게 아니라, 미검(고장을 놓치는 것)의
비용이 훨씬 크다는 전제 하에 절충한 결과라는 걸 명확히 해뒀다.

# 04. 대시보드 구현 — 하이브리드 아키텍처(사전계산 캐시 + 실시간)

Streamlit 멀티페이지로 6개 화면(종합·설비예지보전·품질SPC·생산계획·라인밸런싱·What-if
시뮬레이터·데이터출처)을 구성했다.

## 핵심 설계: 캐시 vs 실시간 하이브리드

What-if 시뮬레이터가 매번 몬테카를로 30회를 새로 돌리면 느리다. 그래서:
- 자주 쓰는 30개 조합(버퍼×PM 그리드)은 **미리 계산해 캐시**(`scenario_grid.parquet`)
- 캐시에 없는 조합만 **그 자리에서 실시간 계산**

실제 측정한 결과:

| 방식 | 소요시간 |
|---|---:|
| 캐시 조회 | 2.15ms |
| 실시간 계산(그리드에 없는 조합) | 658ms |

약 **300배** 차이. 이 구조 덕분에 사용자가 슬라이더를 흔들 때마다 대부분은 즉시 응답하고,
새로운 조합일 때만 "실시간 계산 중"임을 명시적으로 보여준다.

## 페이지 구성

| 페이지 | 내용 |
|---|---|
| 종합 | OEE 워터폴·게이지, 시나리오 선택, 소스별 KPI 요약표 |
| 설비예지보전 | 부품별/설비별 MTBF·MTTR, 고장 파레토, 센서 열화 전조 비교, 비용민감 모델 비교표 |
| 품질SPC | 기존 포트폴리오 산출물(용접 X-bar/R 관리도, Cp/Cpk) 재활용, 비용곡선 임계값 슬라이더 |
| 생산계획 | FCFS/SPT 간트차트, 메이크스팬 비교, 자동 해석 문구 |
| 라인밸런싱 | 목표 Tact 슬라이더, 야마즈미 차트, 이론 최소 스테이션 수 재계산 |
| What-if 시뮬레이터 | 버퍼·PM·Tact 슬라이더 + 실행 버튼, 캐시/실시간 하이브리드 |
| 데이터출처 | 출처·라이선스·이 프로젝트의 한계·재현 방법 |

# 06. 인사이트

## 인사이트 1 — 툴·라이브러리·계산법·깨달은 점

- **KPI 계약을 먼저 정의하고 시작하면, 이후 모든 분석이 "같은 언어로 말한다".** 스키마·
  화이트리스트·검증 함수를 STEP 2에서 미리 만들어둔 덕분에, STEP 6~8의 서로 다른 소스
  (시뮬레이션, ML 모델)의 결과를 별도 변환 없이 하나의 테이블에 모을 수 있었다.
- **몬테카를로 반복 없이 시뮬레이션 1회만 믿으면 안 된다.** 열처리 MTBF 기준 272일 동안
  기대 고장 횟수는 약 3회인데, 실제 1회 실행에서는 1회만 발생해 Availability가 이론값보다
  훨씬 높게 나왔다(포아송 근사로 이 확률이 약 15%나 됨을 확인). 이게 STEP 7에서 "왜 반복
  실행이 필요한가"를 직접 증명하는 근거가 됐다.
- **Kaleido(PNG 내보내기)가 받침 있는 한글을 90도 회전된 축 제목으로 그릴 때 깨지는 버그를
  발견했다.** "공정" → "굣0/ㄷ0"처럼 깨지는데, 받침 없는 글자(시간, 가)는 멀쩡했다. 여러
  차트 종류로 재현해 Kaleido/Chromium의 CJK 폰트 셰이핑 문제로 특정했고, 회전 축 제목 대신
  가로 텍스트 주석으로 대체하는 공통 헬퍼 함수를 만들어 전체 차트에 일괄 적용했다.
- **로컬에서 잘 되던 게 배포하면 깨질 수 있다.** 설비예지보전 페이지가 앱 실행 중에
  80MB짜리 원본 CSV를 직접 읽고 있었는데, 로컬엔 원본이 있어서 몰랐다가 배포 직전에야
  발견했다. 계산을 미리 해두고 결과만 저장하는 방식으로 바꿔서 해결했다(자세한 내용은
  STAR 사례 참고).

## 인사이트 2 — 확장 구상

- **MES/PLM 연계**: 지금은 정적 CSV/parquet을 읽지만, 실제 라인이라면 MES에서 실시간
  생산 실적을, PLM에서 공정 설계 변경 이력을 받아와야 한다. KPI 계약(스키마)이 이미
  `source` 컬럼으로 출처를 구분하도록 설계되어 있어서, MES 연동을 새로운 `source`로
  추가하는 방식으로 확장 가능하다.
- **실시간 IIoT 스트리밍**: 현재 센서 열화 전조 분석은 배치(24시간 윈도우 평균)로 계산한다.
  실제로는 Kafka/MQTT 같은 스트리밍 파이프라인으로 telemetry를 실시간 수집해서, 임계값을
  넘는 순간 알람을 띄우는 구조로 발전시킬 수 있다. 이번 프로젝트의 "고장 직전 24시간 평균
  vs 평상시 평균" 비교 로직이 그 알람 규칙의 출발점이 될 수 있다.
- **버퍼 효과를 보려면 시뮬레이션 기간을 늘려야 한다**: 8시간 시프트에서는 버퍼 효과가
  전혀 안 보였는데, 이는 실측 MTBF가 매우 높기 때문이다(신뢰성이 좋다는 뜻이기도 하다).
  버퍼의 실제 가치를 보여주려면 수백 일 단위로 시뮬레이션 기간을 늘리는 후속 작업이 필요
  하다 — 이번엔 시간 관계상 미착수.

> 캐시/실시간 하이브리드 구조(300배 응답속도 차이)를 설계했으며, Streamlit Community Cloud에
> 실제 배포하는 과정에서 로컬에서는 드러나지 않던 원본 데이터 의존성, 패키지 누락 등 3건의
> 실전 문제를 발견하고 해결했습니다.

# 부록 C. 트러블슈팅 STAR 정리

## STAR 1 — Kaleido의 한글 받침 렌더링 버그

- **Situation**: 대시보드 PNG를 포트폴리오용으로 내보냈는데, "공정" 같은 y축 제목이
  "굣0/ㄷ0"처럼 깨져 나왔다. "시간(초)"는 멀쩡했다.
- **Task**: 왜 특정 한글만 깨지는지 원인을 밝히고, 8개 차트 전체에서 재발하지 않게 고쳐야
  했다.
- **Action**: 받침 있는 글자(공, 정, 병, 목)와 없는 글자(시, 간)로 나눠 순수 `go.Bar` 최소
  재현 코드를 여러 개 만들어 비교했다. 결과, "받침 있는 글자 + 90도 회전" 조합에서만
  재현됐다. Plotly의 기본 y축 제목은 항상 회전되므로, 회전을 아예 안 쓰는 방향으로 접근을
  바꿔 y축 제목을 가로 텍스트 주석으로 그리는 공통 헬퍼(`set_horizontal_yaxis_label`)를
  만들고 전체 차트 함수에 적용했다.
- **Result**: 8개 PNG 전부 육안 확인으로 정상 렌더링 확인. 이후 만든 모든 차트가 이 헬퍼를
  기본으로 쓰게 됐다.

## STAR 2 — SPT가 FCFS보다 80% 더 나쁘게 나온 이유 규명

- **Situation**: "SPT(최단처리시간 우선)가 FCFS보다 항상 낫다"는 일반적인 통념과 반대로,
  시뮬레이션에서 SPT의 메이크스팬(1038.6초)이 FCFS(575.9초)보다 오히려 80.3% 나쁘게 나왔다.
- **Task**: 이게 로직 버그인지, 실제로 있을 수 있는 현상인지 판단해야 했다.
- **Action**: 버그로 단정하지 않고 개별 잡별 시작·종료 스케줄을 전부 출력해서 확인했다.
  특정 잡(여러 공정에서 처리시간이 긴 잡)이 매 공정마다 SPT 규칙 때문에 계속 뒤로 밀려
  대기시간이 누적되는 패턴을 발견했다 — 현장의 "장기물 방치" 문제와 동일한 메커니즘이었다.
- **Result**: 로직을 고치지 않고 이 현상을 "SPT는 단일공정 평균흐름시간엔 유리하지만
  다단계 플로우샵의 메이크스팬은 보장하지 않는다"는 정직한 발견으로 대시보드에 그대로
  노출했다. 통념을 검증 없이 받아들이지 않고 데이터로 확인하는 습관을 다졌다.

## STAR 3 — 배포 직전 발견한 숨은 원본 데이터 의존성

- **Situation**: Streamlit Community Cloud 배포를 준비하며 원본 데이터(`data/raw/`, 131MB)를
  저장소에서 빼기로 했는데, 설비예지보전 페이지가 실행 중에 80MB짜리 telemetry CSV를 직접
  읽고 있다는 걸 뒤늦게 발견했다. 로컬 환경엔 원본이 있어서 이전 QA에서는 문제가 안 드러났다.
- **Task**: 배포하면 바로 깨질 상황이었다. 계산 로직 자체는 바꾸지 않으면서, 원본 의존성만
  없애야 했다.
- **Action**: 해당 계산(고장 파레토, 센서 전조 비교)을 별도 스크립트로 분리해 미리 실행하고,
  결과만 `data/interim/`에 저장한 뒤 페이지는 그 결과만 읽도록 구조를 바꿨다. 수정 전후
  계산값이 정확히 같은지(volt 176.169, rotate 417.220 등) 먼저 대조한 뒤 교체했다.
- **Result**: 배포에 필요한 데이터가 131MB → 약 116KB로 줄어 Git LFS 없이 배포할 수 있게
  됐다. 이후 실제 배포·재배포 과정에서 `openpyxl` 패키지 누락, 차트 텍스트 겹침 등 2건의
  추가 문제도 같은 방식(원인 규명 → 최소 수정 → 재검증)으로 해결했다.
